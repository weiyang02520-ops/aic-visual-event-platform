## 1. Objective

Implement the generic object-location memory core needed for the competition's central problem:

- "Where was this object last seen?"
- "What location/zone was it observed in?"
- "When was it last observed?"

This must remain a generic AI-layer capability, not a workshop-specific rule.

The memory layer must be conservative about identity: track IDs are valid only within their source and continuity segment unless stronger explicit identity evidence exists. Do not invent cross-camera or post-gap identity continuity.

No frontend feature work belongs in this task.

## 2. Current State

- TASK-0006 established canonical COCO17 skeleton observations.
- `CentroidTracker` uses class gating + Hungarian minimum-cost assignment and resets after discontinuities.
- `RelationEngine` already produces motion, near/pickup/putdown candidates and zone enter/leave edges.
- `WorkshopStateReasoner` contains scene-specific removed/returned/missing state, but there is no generic reusable "last known object location" memory core.
- `object_detected` facts contain tracked subject IDs and bbox metadata/object geometry.
- Explicit source_id and continuity_segment provenance already exist.
- Full AI baseline after TASK-0006: 380 passed / VERIFY_OK.

## 3. Requirements

### 3.1 Add a generic object-location observation fact

Extend the relation/fact layer with a reusable current-location fact for non-person objects when configured zones are available.

Use a clear fact name such as `object_in_zone` or `object_location_observed`.

The fact must contain:
- object track/entity identity;
- object label;
- zone_id and human-readable location;
- timestamp;
- confidence;
- source_id and continuity_segment after FrameFactExtractor propagation.

This is a per-observation semantic fact, not a high-level event. It may be emitted repeatedly while an object remains visible in a zone.

Do not treat persons as stored objects for this fact.

### 3.2 Add a generic visual-memory module

Create a small AI-layer module (for example `visual_memory.py`) that consumes PrimitiveFacts and maintains/query object memory.

A memory record must expose at least:
- source_id;
- continuity_segment;
- track/entity ID;
- label;
- last_seen_at (timezone-aware UTC);
- last bbox when available;
- current/last observed zone_id + location when available;
- confidence;
- state/provenance sufficient to explain whether the location is direct observation or only last-known history.

The module must not depend on a scene plugin, frontend or database.

### 3.3 Conservative identity boundary

Default identity key must include:
- source_id;
- continuity_segment;
- track/entity ID.

Rules:
- same numeric track_id from another source is a different object identity;
- same track_id after a continuity gap is a different continuity identity;
- two simultaneous objects with the same label remain separate;
- label alone must never merge active tracked identities;
- heuristic registry_matches may be carried as hints/provenance but must not silently override track identity or claim ReID.

If stronger identity evidence is absent, memory may expose "last seen candidate/history" by label, but it must not claim that two separate tracks are the same physical item.

### 3.4 Memory update semantics

At minimum handle:
- `object_detected`: update last_seen_at, bbox, label and confidence;
- object-location fact: update zone/location as directly observed;
- `entered_zone`: update zone/location when object identity is compatible;
- `left_zone`: remove current-zone certainty while retaining last-known history;
- `observation_gap`: prevent pre-gap track state from being treated as continuous post-gap identity.

Do not infer "missing", "returned", "picked up" or "carried" solely from memory in this task; those remain reasoner/action responsibilities.

### 3.5 Tracker audit

Audit the current `CentroidTracker` against the new memory identity requirements.

Only make a narrow tracker change if a concrete deterministic bug is found.

Do NOT add ByteTrack/Kalman merely because reference documents mention them. Instead document:
- current Hungarian/centroid behavior;
- its identity limitations;
- why ByteTrack/Kalman remains an optional future adapter without dataset evidence.

### 3.6 Deterministic end-to-end tests

Add tests proving:
1. one object observed in zone A becomes queryable as last seen in A;
2. the same tracked object later observed in zone B updates to B;
3. two same-label tracks remain independent;
4. same track_id across two sources never merges;
5. same track_id across a continuity gap never merges;
6. leaving a zone does not fabricate a new location;
7. person detections do not populate object-location memory;
8. source/timestamp/continuity/bbox/confidence remain explainable in the record;
9. no raw image/pixel data enters memory records.

Include at least one integration path using existing FrameFactExtractor + configured zones rather than testing only isolated helper objects.
