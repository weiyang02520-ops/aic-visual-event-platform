## 1. Objective

Start AI algorithm finalization by making skeleton data a first-class, validated algorithm contract instead of an incidental three-keypoint metadata field.

The current real Ultralytics pose path is proven, but the adapter intentionally keeps only nose/left_wrist/right_wrist even though the model exposes COCO17. Preserve the existing medication action behavior while expanding the reusable skeleton layer for privacy-aware visual memory and future actions.

No frontend feature work belongs in this task.

## 2. Current State

- Real local video -> OpenCV -> real Ultralytics pose -> tracker -> PrimitiveFact is already proven.
- `UltralyticsProvider` currently declares `keypoint_schema = "coco17"` but normalizes only:
  - nose
  - left_wrist
  - right_wrist
- `KeypointActionExtractor` correctly consumes nose/wrist geometry for `hand_to_face`.
- Fixture input can carry explicit keypoints and therefore already demonstrates that upper layers need not read raw pixels directly.
- Privacy sanitizer removes pixel-bearing fields while preserving semantic pose/keypoint metadata.
- Full suite baseline: 371 passed / VERIFY_OK.

## 3. Requirements

### 3.1 Canonical skeleton contract

Create one canonical COCO17 definition owned by the AI layer.

It must include the standard names in index order:

```text
nose
left_eye
right_eye
left_ear
right_ear
left_shoulder
right_shoulder
left_elbow
right_elbow
left_wrist
right_wrist
left_hip
right_hip
left_knee
right_knee
left_ankle
right_ankle
```

Do not duplicate independent name/index maps across modules.

Provide a small validated helper/dataclass/type for a normalized skeleton/keypoint observation. It must preserve:
- schema/version;
- named keypoints;
- finite x/y;
- finite confidence in [0,1];
- source/timestamp/track association where that information exists;
- missing/occluded keypoints without inventing coordinates.

Do not require every frame to contain all 17 valid points.

### 3.2 Ultralytics full pose normalization

Update `UltralyticsProvider` so the default COCO17 path exports every available valid COCO17 keypoint, not only nose/wrists.

Requirements:
- existing custom `keypoint_indices` injection remains supported if it is part of the current public test contract;
- malformed/non-finite values still fail closed consistently;
- missing points may be omitted;
- no image pixels enter the normalized skeleton contract;
- provider metadata remains truthful about provider/schema/version.

### 3.3 Existing action compatibility

The medication action path must continue using the canonical skeleton contract but must preserve current behavior:
- nose + left/right wrist geometry remains sufficient;
- absence of unrelated COCO17 joints must not break `hand_to_face`;
- one-frame keypoint dropout/debounce/source/timestamp protections remain intact.

Refactor only as needed to avoid multiple incompatible keypoint parsers.

### 3.4 Skeleton-only upper-pipeline proof

Add deterministic regression coverage proving the upper AI path can operate on precomputed skeleton/keypoint observations without raw image pixels.

At minimum prove:
- an explicit person skeleton plus an explicit medication/object observation can pass through existing normalization/fact/action logic;
- semantic skeleton/keypoint data survives privacy sanitization;
- raw image/gray/RGB/BGR/pixel data is absent from the produced facts;
- source_id, timezone-aware timestamp, track identity and continuity metadata remain preserved;
- the expected reusable action fact can still be produced when geometry supports it.

This is a software-contract test, not a claim that a physical camera already emits skeleton-only data.

### 3.5 Documentation

Update the AI algorithm docs to define two privacy deployment modes:

```text
Mode A — current/local:
RGB frame -> pose provider -> skeleton -> upper AI

Mode B — target edge-privacy boundary:
camera/edge pose -> skeleton-only payload -> upper AI
```

Clearly state:
- Mode A is implemented with the real Ultralytics runtime smoke;
- skeleton-only upper-pipeline behavior is software-tested;
- physical camera/edge skeleton-only output is not yet hardware-verified;
- cartoon rendering belongs to frontend/presentation and is outside this task.
