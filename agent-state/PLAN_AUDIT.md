## 可以保留的主线

1. AI 独立于 Makerverse 和 livestream-rs，先用接口适配，避免重写既有后端。
2. 视觉底座产生人、物、轨迹、关系和基础事实，场景插件负责业务解释。
3. 事件统一、保存证据时间窗、支持人工复核，并明确使用“疑似/证据不足/待复核”等表述。
4. 前端同时提供 Mock 与 Real provider，后端联调受阻时仍能完成演示。
5. 机器人作为后续感知/执行载体，具体硬件能力要等资料到位后再写入方案。
6. 不把 Mock、目标指标或未来机器人能力写成已验证事实。

## 高优先级问题

### P0-A：版本叠加导致权威内容不明确

文件名是 `V5_FINAL`，正文开头写 `V3.0`，后面又附有 `V1.0` 的上一版规格，并在末尾加入 `V5 最终执行细化`。计划中声明冲突时以 V3 为准，但 V5 细化又出现在后面，容易让执行者误读。

处理方式：当前按“用户最新明确要求 > 老师文档与官方赛道规则 > 正文 V3 主体 > 附录旧版”解释；V5 细化仅作为补充，不能覆盖前面已经确认的范围。真正开始编码前，应生成一份去重后的 `EXECUTION_BASELINE.md`，记录生效条款和被废弃条款。

### P0-B：目录结构有两套写法

早期章节使用 `workspace/ai-engine`、`workspace/frontend`、`workspace/docs`、`workspace/agent-state`、`workspace/submission`；附录又使用 `ai-dev`、`frontend-dev`、`integration-notes`、根目录 `agent-state` 和 `submission`。当前已采用根目录 `agent-state/` 加 `workspace/{ai-engine,frontend,docs,submission}/`，因为它能同时满足状态与提交隔离；后续不要再创建第二套平行目录。

### P0-C：最终赛道没有锁定

计划书把智慧养老作为主场景、工作室作为辅助场景、机器人作为落地载体，但这只是当前方案叙事，不能直接当作比赛赛题。用户给出的官方通知页面当前明确描述的是“算法挑战赛道”，列出的赛题包括多模态视觉理解、城市场景视觉多模态目标检测、无人机语义分割、噪声标签细粒度识别和虚拟染色图像生成；这与养老/工作室/机器人应用是否属于同一报名赛道仍需老师确认。

处理方式：在老师主文档和最终赛道确认前，代码保持通用、文档保留可裁剪的多场景材料；不要声称已经满足某一道赛题的评分要求。

### P0-D：“AI 算法从头弄”没有被定义

计划书同时提出“通用视觉底座、可替换成熟检测器/跟踪器、embedding 注册、规则状态机”，并禁止从零训练大型视觉模型。这并不等同于比赛所说的自研算法。需要在老师要求到位后明确：是要求从零实现业务事件推理，还是要求训练/微调特定视觉模型，还是两者都要。

处理方式：默认先做可解释的事件推理、时序聚合、置信度和证据检索基线；任何模型训练指标、数据集和自研程度都标记为待赛题确认，不能先写成创新成果。

### P1-E：范围过宽，验收矩阵缺少阶段性优先级

计划同时覆盖视频输入、检测、跟踪、关系、插件、养老、工作室、自定义物品、人员、REST、WebSocket、前端多页面、真实后端、机器人占位、比赛材料、LaTeX 和近百个测试用例。没有明确时间、硬件、数据集和人员投入时，全部按 P0 执行会导致“完成很多接口但没有可展示闭环”。

处理方式：先锁定一个可演示闭环：本地视频/合成帧 → 基础事实 → 一个场景事件 → SQLite → API → 前端事件与证据窗口。再扩展第二场景、真实流、Makerverse 和机器人 adapter。

### P1-F：视频证据链契约还不完整

计划要求 AI 不保存视频、只保存事件和 evidence 时间窗，但没有冻结 `source_id`、时间戳基准、录像分段命名、时区、保留期、播放 URL 生成和删除策略。没有这些字段，前端无法可靠跳回 livestream-rs/MinIO 的历史证据。

处理方式：Phase 0 先写 `EVIDENCE_CONTRACT.md`，至少确定事件时间、流时间、分段时间、播放地址解析失败时的降级展示，以及 AI 与 livestream-rs 时钟不同步时的处理。

### P1-G：机器人资料缺失是实质性阻塞

当前没有机器人型号、相机输出、ROS/HTTP/串口协议、网络拓扑、运行平台、控制安全边界和老师要求的真实演示方式。计划中所有“寻物/带路/取物”都只能是未来方案描述，不能进入已完成清单。

### P1-H：测试矩阵需要真实夹具和环境前提

测试用例大多只写了“构造最小可重复输入”，没有明确视频 fixture、模型权重、GPU/CPU、FFmpeg、Node、Python 版本和浏览器播放条件。后续应把每个测试标记为 deterministic unit、API contract、frontend smoke、real integration 或 hardware required，并记录未执行原因。

## 当前采用的执行解释

```text
资料根目录
├─ agent-state/                 # 长任务状态，不进入提交包
├─ workspace/
│  ├─ ai-engine/                # 独立 AI 工程
│  ├─ frontend/                 # 前端工程
│  ├─ docs/                     # 项目与比赛材料
│  └─ submission/               # 干净交付目录
└─ Codex_Master_Execution_Plan_V5_FINAL.md
```

阶段顺序采用：

1. 资料、赛道、仓库和环境事实审计；
2. 最小 AI 闭环和统一事件契约；
3. 插件发现与一个主场景插件；
4. Mock 前端完整演示；
5. 第二场景与真实流适配；
6. Makerverse、证据链和机器人资料到位后的低风险集成；
7. 实验、文档融合与干净 submission。

## 暂不应写成已完成的内容

- AIC 最终报名赛道及其评分达标；
- 养老服药识别准确率、Recall、F1、FPS 或真实老人测试；
- Makerverse 与 livestream-rs 的实时生产联调；
- 机器人已导航、抓取、带路或取物；
- 任意自定义物品都能稳定识别；
- 从零训练算法已经完成。
